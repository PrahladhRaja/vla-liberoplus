# Adding your work to vla-liberoplus

This repo holds the whole team's work on LIBERO, LIBERO-Plus and small VLAs. To keep it usable, every contribution
follows the same layout and rules. When in doubt, look at how the TurboVLA work is organized and mirror it.

## 1. Where things go
Use one short, lowercase name for your model or study throughout, for example `smolvla` or `nafnet`.

| What | Where | Example (existing TurboVLA work) |
|---|---|---|
| Your written summary: what you did, what you found, open questions | `teammates/<your-name>.md` | — |
| Environment / container setup, job scripts for training and evaluation | `cluster/<model>/` with a `README.md` | `cluster/finetune_lp/`, `cluster/liberoplus_container/` |
| An eval-kit adapter for your model, if you use our kit | `cluster/eval_kit/adapters/<model>.py` | `adapters/turbovla.py` |
| Scripts for a specific experiment or test | `experiments/<topic>/` | `experiments/robustness/` |
| Plans and logs of experiments | `docs/plans/PLAN_<topic>.md` | `docs/plans/PLAN_test1_instruction_leak.md` |
| Per-task results | `results/<model>/<run name>/` | `results/turbovla/lp_eval_ft/` |
| Written reports or tables | `results/<model>/reports/` | `results/turbovla/reports/` |
| Changes to someone else's code (LeRobot, openpi, …) | `patches/<project>/` as `git format-patch` files, plus a row in `third_party/VERSIONS.md` with the exact upstream commit | `patches/openvla-oft/` |

Don't edit another person's folders without asking them. Shared files are: `README.md`, `docs/findings/*`,
`third_party/VERSIONS.md` and `THIRD_PARTY_LICENSES.md`. Change those in the same pull request as your work, and
mention it in the description.

## 2. Results format
Results only count if they can be compared task by task with everyone else's.

1. **One record per task.** Preferred: our `results.jsonl`, one JSON object per line:
   ```json
   {"suite": "libero_goal", "task_id": 1000, "success": true, "seconds": 14.2}
   ```
   - Add `"instruction_fed"` / `"instruction_official"` if you change the instruction.
   - A CSV with the same columns (`suite,task_id,success,seconds`) is fine too.
   - `task_id` is LIBERO-Plus's 0-based index within the suite, the same as in our `plan.tsv`.
2. **Include the task list** (`plan.tsv` or equivalent) and the run's config file.
3. **Add a protocol card** (`results/<model>/<run>/PROTOCOL.md`) with:

   | Setting | Value |
   |---|---|
   | Model and checkpoint (Hugging Face id + revision, or training run) | |
   | Task set (all 10,030, or which subset) | |
   | Initial state, settling steps | (ours: state 0, 10 steps) |
   | Max steps per suite | (ours: 220 / 280 / 300 / 520) |
   | Actions executed per model query | |
   | Instructions: official LIBERO-Plus or cleaned | |
   | Env seed | (ours: 7 for TurboVLA, 0 for OpenVLA-OFT) |
   | Simulator: MuJoCo, robosuite versions; machine | (ours: 3.2.0, 1.4.1, Turing A30) |
   | Trials per task | (ours: 1) |

   Results that differ from our protocol can still go in the repo. The card decides whether they are compared task by
   task with ours, or shown only as a separate reference point.
4. **Name runs after what they are**, e.g. `lp_eval_<model>` for the full official benchmark and
   `lp_eval_<model>_clean` for clean instructions.

## 3. Never commit
- **Model weights or checkpoints** (`.pth`, `.pt`, `.safetensors`, …). Link to Hugging Face or a Turing path instead.
- **Videos, eval logs, datasets and archives.** Keep them on Turing (`/scratch`, `/archive`) and describe where in your
  summary.
- **Secrets:** passwords, Hugging Face or GitHub tokens, SSH keys.
- **Hard-coded personal email addresses** in job scripts. Use `${MAIL_USER:+--mail-user=$MAIL_USER}` on the `sbatch`
  command line instead of `#SBATCH --mail-user=…`.
- **Code from LIBERO-Plus.** It declares no license. Clone it at the pinned commit instead.

`.gitignore` blocks most of these, but check `git status` before committing.

## 4. Licenses
- **Your contributions** are under the repo's Apache License 2.0.
- **Copied third-party files** keep their original license header. Add the project to `THIRD_PARTY_LICENSES.md`
  (and to `NOTICE` if its license requires attribution).
- **Gemma terms for π0.5-trained models:** a model trained on demonstrations generated by π0.5 (Gemma Terms of Use)
  is a Gemma "Model Derivative". This matters only if you publish its weights; note it in your summary.

## 5. Workflow
1. Make a branch: `git checkout -b <your-name>/<topic>`.
2. Commit in small, described steps. One topic per pull request is easiest to review.
3. Open a pull request into `main`. In the description, list:
   - what you added;
   - which shared files you changed;
   - anything that needs a Turing path or checkpoint to reproduce.
4. The repository owner reviews and merges.

## 6. Running on Turing
- **Rules:** read `docs/turing/AGENTS.md` and the Turing docs before running anything. Heavy work only through SLURM,
  always with `--time`. Use only your own files and jobs.
- **Scripts:** this repo's scripts assume their folder sits at a fixed place in your Turing home directory (see the
  table in `README.md`).
